\section{Research Questions}

Coding agents spend much of their budget on routine decisions. We ask whether a structured decision model can replace one narrow component of an existing coding agent at lower total cost and latency while preserving bug-repair success. Following the instructor's advice to obtain mechanical evidence inside an existing harness before redesigning one, we replace the repository-exploration subagent of OpenCode with deterministic file retrieval plus one typed Jev decision that chooses which files the agent should inspect; the same strong model still writes and tests every patch. We address three questions. (Q1) Does the substitution preserve repair success while reducing cost and wall time? (Q2) Does Jev choose relevant files better than retrieval alone? (Q3) Does better file choice translate into better repairs, and under what conditions? Repair success is graded by each issue's own regression tests; cost is the billed total of all model calls; time is agent wall time.

\section{Environment \& Data}

\paragraph{Harness and tools.}
We use the pinned OpenCode 1.19.5 command-line harness with its native build agent, \texttt{task} delegation tool, \texttt{explore} subagent and file tools \citep{opencode}. Each rollout starts from an exact upstream snapshot without git history. The issue prompt asks the build agent (the \emph{writer}) to delegate localization to the explorer before editing, then implement a minimal fix and optionally run existing tests; it is identical across conditions. The writer keeps its own \texttt{read}, \texttt{grep} and \texttt{glob} tools and may edit only implementation files, never tests. These are tool permissions, not an operating-system sandbox.

\paragraph{Tasks.}
All tasks are real GitHub issues with upstream fixes and regression tests from SWE-bench \citep{swebench}; no task was invented. (i) \emph{Development pilot}: the five pydicom issues of the SWE-bench Lite development split \citep{dataset}. (ii) \emph{Extended development run}: the remaining \AgFrozen{} pydicom issues of the full SWE-bench development split; \AgValid{} pass our environment controls and \AgDropped{} are dropped and listed because even their upstream fix fails in the pinned environment (removed NumPy APIs, Python 3.12 behaviour). (iii) \emph{Verified pilot}: ten tasks from SWE-bench Verified, a human-screened 500-task subset of the test split \citep{verified,verifieddata} (five Django, two SymPy, one each from Matplotlib, scikit-learn and Sphinx), drawn by stratified hash ordering from a frozen 50-task sample using only instance IDs. (iv) \emph{File-selection study}: all \LocTotal{} issues of the SWE-bench development split across six repositories. Every task list, base commit and protocol was committed before any outcome was observed. The SWE-bench test split outside the Verified sample is reserved for held-out final evaluation. Public issues may appear in model training data; we make no contamination-free claim.

\paragraph{Evaluation and success criteria.}
Development patches are applied with the benchmark's test patch to a fresh snapshot and graded by the published fail-to-pass and pass-to-pass tests under pinned local pytest; before any paid run every environment is validated (the broken base fails, the upstream fix passes). This local grading is not an official SWE-bench score. Verified patches are graded by the official \texttt{swebench} 5.0.2 Docker harness; every image was checked to contain no test patch, gold fix or later upstream history, and every gold fix resolves. For file selection, an issue's \emph{gold files} are the implementation files its upstream fix modifies; the primary metric is \emph{hit@3}, a gold file among the three chosen files, with candidate recall (a gold file among the 12 candidates) as its ceiling. Gold assets are read only by graders and scorers, never by the agent or Jev.

\section{Methods}

\paragraph{One internal substitution.}
The writer is \texttt{openai/gpt-6.1-sol} in every condition. A thin OpenAI-compatible adapter exposes separate build and explore endpoints, so OpenCode's own \texttt{task} tool still creates the explorer session and returns its report to the writer. In the \emph{native} condition the explorer is a GPT-6.1-Sol subagent with read-only tools. In the \emph{Jev} condition only the explorer's model call is replaced: a deterministic BM25-style search over implementation files ranks candidates against the writer's exploration request, the top 12 with their most query-matching 16-line windows go to Jev 1.14, which answers one Noul relevance question per file in a single call \citep{jev}, and the three highest-scoring files are returned. Jev writes no code and selects no model; on an API or validation error the native explorer is used and both costs are counted. Scores are not calibrated probabilities and no threshold is applied. The \emph{search} control returns the top three retrieval candidates without Jev, testing whether any benefit needs the decision model. The extended run adds an \emph{oracle} that returns the files the upstream fix changes (paths and snippets only), an upper bound on what better localization can buy.

\paragraph{File-selection study and sweep.}
The offline study reuses the identical retrieval and Jev question, generalized to each repository's package directory; it reproduces the development pilot's ten archived candidate lists exactly. Its query is the issue text rather than the writer's exploration request. A separately frozen sweep repeats it with 24 and 48 candidates.

\paragraph{Limits, accounting and timing.}
All conditions share 16 writer steps, 6 explorer steps, at most 32 requests, 4,096 output tokens per request and 480 s per run; the Verified runner refuses to run if any shared setting differs. The adapter records every billed response; durable ledgers cap spending per run and per experiment, and the coding process never receives the real API key. The extended run splits time into exploration (retrieval plus the Jev decision, or the native explorer's calls), writer calls and grading. Conditions run in four parallel lanes with per-issue shuffled order, so load affects all conditions alike. Every run archives its protocol hash, trace, receipts, file decisions, patch and test log.

\paragraph{Q1: the substitution saves a third of time and cost without changing success.}
In the extended run (Table~\ref{tab:agent}), Jev changed mean agent time by $\AgJevNativeTimeS$~s per issue relative to native (\AgJevNativeTimePct\%; 95\% paired bootstrap interval $\AgJevNativeTimeLow$ to $\AgJevNativeTimeHigh$~s) and cost by \AgJevNativeCostPct\%. Almost all of the saving is exploration (\AgNativeExplore{}~s of model calls for native, \AgJevExplore{}~s for retrieval and one decision); writer time is similar across conditions. Success did not differ: \AgNativePassed, \AgJevPassed, \AgSearchPassed{} and \AgOraclePassed{} of \AgValid{} issues for native, Jev, search and oracle, with at most three discordant issues per pair. The pilots agree (Table~\ref{tab:results}): on Verified, native and Jev each resolved \VNativePassed/10 and search \VSearchPassed/10, while cost fell from \$\VNativeCost{} to \$\VJevCost{} (\VSavings\%) and time from \VNativeTime{} to \VJevTime{}~s; Jev's ten decisions replaced \VNativeExploreCalls{} explorer generations. No run timed out, fell back or made a forbidden edit.

\paragraph{Q2: Jev chooses files better than search.}
Across \LocN{} issues (Table~\ref{tab:loc}), Jev placed a gold file among its three choices for \LocJev\% of issues, against \LocSearch\% for search and \LocRandom\% for a random choice among the same candidates: a paired gain of \LocDiff{} points (95\% interval \LocLow{} to \LocHigh{}; \LocWins{} wins, \LocLosses{} losses, sign test $p \LocP$). When retrieval found a gold file, Jev chose one \LocJevCond\% of the time versus \LocSearchCond\%, so retrieval recall (\LocRecall\%) is now the ceiling. Longer shortlists raise it: with 24 and 48 candidates hit@3 rose to \SwHitTwentyFour\% and \SwHitFortyEight\%, recovering \SwRescueTwentyFour{} and \SwRescueFortyEight{} of the \SwNear{} issues whose gold file missed the 12 (gain over 12 at 24: \SwDiffTwentyFour{} points, 95\% interval \SwLowTwentyFour{} to \SwHighTwentyFour{}, $p \SwPTwentyFour$), while keeping \SwKeptTwentyFour{} of the \SwKeptBase{} issues already solved. Median decision latency stayed below half a second (\SwLatTwelve, \SwLatTwentyFour{}~s), but at 48 candidates \SwSlowFortyEight{} of \SwN{} decisions took about 8~s; 24 candidates capture most of the gain without that tail. The three studies cost \$0.29 in total.

\paragraph{Q3: better selection does not yet change repairs, because the writer recovers.}
Inside the agent, Jev's report named a gold file far more often than search's (Table~\ref{tab:agent}), yet Jev and search did not differ in success, time ($\AgJevSearchTimeS$~s, interval $\AgJevSearchTimeLow$ to $\AgJevSearchTimeHigh$) or cost (\AgJevSearchCostPct\%). On the 13 issues where only Jev's report contained a gold file, both repaired 4. The traces show why: after delegating, the writer immediately runs its own \texttt{grep} and \texttt{read} calls, follows the code's references and reaches the gold file itself, which is fast and almost free. Its final patch edited a gold file in 95\% of extended runs whatever the explorer reported, and in all 30 Verified runs although Jev's and search's top three contained it only \VJevGoldReturned/10 and \VSearchGoldReturned/10 times, including on Django's large codebase. Editing the right file is necessary (no patch that missed every gold file passed, 0 of 8) but not sufficient: even the oracle repaired no more issues, so with this writer the limiting step is writing the correct change, not finding the file. The saving therefore comes from not running a generative explorer whose work the writer largely repeats, not from the quality of Jev's choices, and the search control captures it equally. Jev's top score also did not separate correct from incorrect selections in the Verified sample (misses up to 0.85, hits as low as 0.66).

\paragraph{Completed work, obstacles and next steps.}
Completed: the development pilot, a Linux reproduction, the Verified pipeline with image checks, the 30-run Verified pilot, the 164-run extended run, the 675-decision file-selection study and sweep, and 27 offline checks of method equivalence, leakage boundaries, fallbacks and budget denial; every reported number can be recomputed offline from the archives in the project repository (\url{https://github.com/KristjanDagur/CS329zFinalProject}), following its README, except the Verified pilot, whose run directory is still to be archived. Total spend is about \$20 of OpenRouter credit and no Tinker credit. To answer Q3 where selection can matter, we have frozen a protocol in which the writer may read and edit only the files chosen before launch, with no search tools (Jev, search and oracle on the 41 issues); its first smoke run stalled before any writer call, apparently on OpenCode's shared session database, and we are isolating per-run state before running it. The same restriction will be applied to a shared 20-task Verified subset by both arms from one commit, alongside an empty-explorer control and a cheaper writer, which may recover less well. Five or ten single rollouts support no interval claims (2/5 has a 95\% interval of roughly 12\% to 77\%), so the final study will use repeated rollouts and paired bootstrap intervals as in the extended run. We also plan to move Jev to a decision the writer cannot bypass, uncertainty-gated escalation between a cheap and a strong writer with thresholds chosen on independent development data, which returns to our proposal's calibrated-confidence question.

\paragraph{Safety considerations.}
We use public software issues, not clinical data or deployed systems; generated patches are research artifacts and are never merged upstream. Credentials never reach traces or agent processes. Verified tests run in network-disabled containers, but development tests run on the host, and the agent's edits are limited only by tool permissions; future runs should isolate every environment.
