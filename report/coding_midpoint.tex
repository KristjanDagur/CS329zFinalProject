\section{Research Questions}

Our project asks whether a structured decision model can replace a narrow component of an existing coding agent at lower total cost while preserving bug-repair performance. Following the instructor's recommendation to obtain mechanical evidence before redesigning an agent harness, we study OpenCode's repository-exploration subagent. Our intervention uses Jev to select relevant source files from deterministic search candidates; the same strong generative model continues to write and test patches. We compare this intervention against the native generative explorer and a search-only replacement. The primary outcomes are independently graded repair success and total inference cost.

We report two experiments. A development pilot on five SWE-bench Lite issues fixed the method. A second pilot then applied the unchanged method to ten SWE-bench Verified tasks, selected before any agent run and graded by the official containerized harness. The midpoint objective is a working substitution and an authentic evaluation pipeline, not a claim of calibrated confidence or performance equivalence from small samples.

\section{Environment \& Data}

\paragraph{Existing agent harness.}
We use the pinned OpenCode 1.19.5 command-line harness and retain its native build agent, \texttt{task} delegation tool, \texttt{explore} subagent, file tools, and patch-writing loop \citep{opencode}. Each rollout starts from an exact upstream repository snapshot without upstream git history. The issue prompt asks the build agent to delegate initial localization to the existing explorer before editing, then implement a minimal fix and optionally run existing tests. The prompt is identical across conditions within an experiment. The parent agent retains its own read and search tools and can therefore recover from imperfect localization. Tool permissions allow edits only to the repository's implementation directories, never to tests; these permissions are not an operating-system sandbox.

\paragraph{Development pilot (SWE-bench Lite).}
We used all five pydicom issues in the official SWE-bench Lite development split \citep{swebench,dataset}, chosen for a locally runnable pure-Python environment. Task IDs and base commits were frozen before agent outcomes. Each patch was evaluated by applying it and the benchmark's test patch to a fresh snapshot and running the published fail-to-pass and pass-to-pass tests under pinned local pytest. Every environment was validated beforehand: the broken base fails and the upstream fix passes. This local evaluation is not an official SWE-bench score.

\paragraph{Verified pilot sample.}
SWE-bench Verified is a 500-task subset of the SWE-bench test split whose issues and tests were screened by human annotators for adequate specification \citep{verified}. We pinned dataset revision \texttt{78f471b} \citep{verifieddata} and drew a 50-task sample, stratified by repository in proportion to the full set; within each repository, tasks are ordered by a SHA-256 hash of a recorded seed and the instance ID. The first pilot uses a nested 10-task subset produced by the same rule: five Django tasks, two SymPy, and one each from Matplotlib, scikit-learn, and Sphinx. Selection used only instance IDs and repository names. Both the sample and the protocol were committed before any agent run.

\paragraph{Official evaluation and environment checks.}
Verified patches are graded by the official \texttt{swebench} 5.0.2 harness \citep{swebench} using the published per-task Docker images and a local copy of the pinned rows. Before any paid run, we checked every image. Each contains the base commit plus one harness setup commit and no later upstream history. That setup commit changes no source or test content; it only alters file permissions, except for dependency pins in Sphinx's packaging files. Neither the benchmark's test patch nor the gold fix is present in any image, and all ten gold fixes resolve under the harness. Public issues may appear in model training data, so we make no contamination-free claim.

\section{Methods}

\paragraph{One internal substitution.}
The build agent uses \texttt{openai/gpt-6.1-sol} in every condition. A thin OpenAI-compatible provider adapter exposes distinct build and explore URLs. OpenCode's native \texttt{task} tool still creates an explorer session and returns its result to the parent. In the native condition, both URLs forward to the same strong model, so the explorer is a GPT-6.1-Sol subagent with read-only tools. In the Jev condition, only explore-provider requests are replaced by deterministic retrieval, one typed Jev request, and a formatted list of selected file paths and snippets.

\paragraph{Candidate construction and Jev decisions.}
We index the repository's Python implementation files, excluding tests. A deterministic BM25-style search ranks files against the parent agent's actual exploration request. The top 12 candidates include relative paths and the most query-matching 16-line window of each file, capped at 1,800 characters. Jev 1.14 receives the request and candidates and answers one Noul file-relevance question per candidate in a single API call \citep{jev}. We validate every returned probability and return the three highest-scoring files to the parent. Jev neither writes patches nor selects the coding model. An API error or invalid score falls back to the native explorer, and both costs are counted. No confidence threshold is applied, and relevance scores are not calibrated probabilities of repair success.

\paragraph{Comparisons and fixed limits.}
Each experiment runs three conditions on the same tasks, one rollout each: native exploration, retrieval plus Jev selection, and search-only, which returns the top three retrieval candidates without Jev. The search-only control tests whether any benefit requires the decision model. All conditions share the writer model, tools, evaluator, 16 parent steps, 6 explorer steps, at most 32 requests, 4,096 output tokens per request, and 480 seconds per run. The Verified protocol imports these settings from the development protocol and refuses to run if any of them differ.

\paragraph{Agent-side testing on Verified.}
Verified repositories require version-specific environments, so the agent's test command runs inside the task's official image. Each run starts one container, completes the image's environment setup online, then disconnects the network and replaces the repository's git history with a single fresh commit. The agent may call \texttt{run\_tests} with test targets. The wrapper applies the current workspace diff to a clean copy and invokes the repository's standard test runner with the validated, shell-quoted targets. The benchmark's own test targets, test patch, and gold patch never reach the agent.

\paragraph{Accounting and artifacts.}
The adapter records upstream responses and billed usage for writer, auxiliary, exploration, and Jev calls. A durable ledger reserves conservative costs before requests and settles bills; caps are \$2 per rollout and \$10 for the Verified pilot. The real API key stays in the host adapter. Each run stores its source/protocol hash, task metadata, event trace, request/response receipts, file decisions, test-command log, patch, and grader report. All 30 Verified pilot runs share one source hash, and every bill was captured.

\paragraph{Where the saving comes from.}
The search-only control matched Jev's cost and came within one task of its success, so the experiment does not show that Jev is preferable to deterministic retrieval. Its single additional failure (Django 15695) is not a retrieval failure: search returned the file containing the upstream fix, and the writer edited it but placed its guard after an index lookup that fails. To examine localization separately from success, we compared the returned files with the files changed by the upstream fix. This analysis uses evaluator-side data that never reached the agent. The fix file appeared among the three returned files in \VJevGoldReturned/10 Jev runs and \VSearchGoldReturned/10 search-only runs. Nonetheless, the writer edited that file in all \VEditedGold{} Verified runs. In the traces we inspected where the returned files missed the fix file, the parent issued its own searches immediately after delegating exploration and located the file itself. The saving therefore comes primarily from not running a generative exploration subagent whose work the parent largely repeats, rather than from the quality of Jev's selections. Jev's highest relevance score also did not separate correct from incorrect selections in this sample: misses scored up to 0.85, and hits as low as 0.66. All three conditions failed SymPy 13852, and the development pilot's failures likewise reflected incomplete repairs, not infrastructure errors.

\paragraph{Completed work and next steps.}
We have completed the development pilot, a Linux-validated reproduction, the Verified pipeline with environment checks, and the 30-run Verified pilot. The pipeline has 27 offline checks covering method equivalence with the development protocol, leakage boundaries, test-command validation, and grading edge cases. Next, we will add an empty-explorer control in which the explore call returns no files. If it matches Jev and search, exploration is not the decision through which Jev can matter for this writer. We will then extend to the remaining 40 sampled tasks (about \$9 projected from measured costs) and report paired uncertainty. We also plan to move Jev to a decision that the agent cannot bypass: uncertainty-gated escalation between a cheap and a strong writer, with thresholds chosen on independent development data. The original BANKING77/CLINC150 intent-classification track remains deferred. Training with Tinker credits is conditional on a demonstrated need.

\paragraph{Safety considerations.}
We use public software issues and repository fixtures, not clinical data or deployed systems. Generated patches are research artifacts and are never merged upstream. Credentials are excluded from traces and from agent processes. Agent-side tests run in network-disabled containers, but the agent's file edits are restricted only by tool permissions on the host.
